## 1. 설계 목표와 냉정한 진단

**한 문장 중심 질문:** "카메라의 사과 사진·연속 촬영 동영상은 컴퓨터에서 어떻게 숫자가 되고, 그 숫자에서 결함을 찾는 모델은 어떻게 학습할까?"

### 최우선 학습 목표 (Approved 기획)

**G1. 이미지와 동영상을 컴퓨터가 어떻게 수치 데이터로 받아들이며, 그 때문에 Vision AI가 왜 어려운지를 이해한다.**
- 정지 이미지: Pixel·RGB의 의미, `H×W×3` 배열과 해상도가 보존하거나 잃는 정보를 설명한다.
- 동영상: 압축 영상 파일을 디코딩하면 시간 순서가 있는 여러 Frame을 얻고, 각 Frame은 하나의 이미지 배열임을 이해한다. 교육용 영상 클립의 표현은 `T×H×W×3`이고 `T`는 Frame 수이다. 이는 압축 파일 자체의 데이터 구조나 모든 실제 동영상 모델의 입력 형식과 같다는 뜻이 아니다.
- Vision AI의 난점: 같은 대상도 조명·회전·원근·가림·흐림·움직임에 따라 Pixel 값과 Frame 배치가 달라진다. 큰 변화는 무시하고 작은 지정 결함은 감지해야 하며, 동영상에서는 시간적 순서와 인접 프레임의 높은 유사성도 고려해야 한다.

**G2. 컴퓨터의 머신러닝 모델이 데이터로부터 어떻게 판단 규칙을 학습하는지 이해한다.**
- 사람이 판단 규칙을 직접 지정하는 Rule-based와, 이미지·프레임 및 정답 Label로 Weight를 조정하는 Machine Learning의 차이를 설명한다. **'알아서 학습'은 사람이 목표·Label·Loss·Architecture를 지정한 다음, 데이터로 모델 Weight를 최적화한다는 뜻**이다.
- CNN이 머신러닝(ML) 안의 딥러닝(DL)에 속하는 **이미지 처리에 적합한 신경망 아키텍처 한 종류**임을 설명한다.
- CNN Architecture의 전체 그림을 먼저 본 다음 그림 속 Kernel·Feature Map·ReLU(비선형성)·Stride·Padding·Max Pooling·Channel·Head를 쉬운 숫자 예시로 설명한다.
- `입력 데이터→CNN 특징 계산→예측→Label과 비교→Loss→Gradient/Optimizer→Weight 갱신→반복`의 학습 순환을 직관적으로 설명한다.
- Training과 Inference의 차이를 구분하고, 새로운 촬영 조건에 일반화하는지는 독립 Validation/Test로 확인해야 함을 이해한다.

**세부 학습 성과:** G1·G2를 위한 Task별 Classification/Detection/Segmentation 출력·Label 선택, Perceptron·AND/XOR·ReLU·CNN Kernel/Feature Map의 역할, Train/Validation/Test·FN/FP·Precision/Recall의 의미를 연결한다. 코딩, 수학적 증명, 동영상 Tracking 알고리즘은 범위에서 제외한다.

**강의 인과관계:** **Vision AI란 무엇인가(사과 결함 판정)** → **AI⊃ML⊃DL은 방법, Computer Vision은 이미지·영상 문제 분야** → 왜 필요한가 → Grayscale H×W(2축) → RGB Pixel(3값) → RGB 전체 H×W×3(3축) → **같은 사과의 RGB Frame 여러 장을 시간순으로 나열한 동영상 T×H×W×3(4축)** → Vision의 어려움(G1) → Task·Rule-based vs ML → CNN이 필요한 이유→CNN 전체 Architecture→각 요소 확대→데이터/Label·Loss·Weight 학습→독립 평가(G2).

**장점:** 같은 사과 검사 사례, 실제 클릭 Pixel/RGB, 명확한 덧셈 규칙 2예제, AND/XOR 슬라이더, 동일 5×5/3×3 Kernel→Feature Map 연속 수치, SqueezeNet 실제 일부 특징 출력, 동일 교육용 평가 100건의 내부 일관성.
**P0:** I13은 I09~12의 원인/사례를 반복한다; C11은 ReLU를 소개하기 전에 `|t|` 비선형 효과를 조작해 선행지식이 뒤바뀐다; C42~44는 워크플로·과제정의·Threshold 실습을 중복한다.
**P1:** 현행 Intro의 정지 이미지 Pixel 설명은 풍부하지만 동영상의 Decoder→Frame→시간축은 독립적으로 설명되지 않아 Video Group Split의 선행지식이 부족하다. C04/C05/C06에는 기존 모델과 방법 선택의 반복이 있다; C14가 CNN 전체 Architecture부터 먼저 시작해 "왜 지역·공유 구조인가?"라는 요구가 C15에 늦게 나온다; C27의 비디오 그룹 예시는 사과 연사/같은 제품 그룹과 추가 연결이 필요하다; CNN의 30분 11장은 압축하지 말고 계산 중심 우선순위를 구분해야 한다.
**기술적 주의:** 단일 뉴런의 가중치 개수 ≠ 뉴런 수. 공유 W의 `z=W(x1+x2)+b`는 특별 예시. AND 실습은 `z=Wx1+x2+b`이며 같은 W 가정과 다르다. Affine 합성은 Affine. XOR 비선형 예시의 `|t|`는 ReLU 두 개의 합. C34 고정 Backbone의 후단 지도/비지도 활용 ≠ 전체 CNN 학습 방법의 구분. 고정 Score는 calibrated probability가 아니다.

### Intro와 CNN을 설명하는 순서

1. **P01~P03:** 사과 사진·연속 영상 입력→AI 기반 결함 분석이라는 Vision AI의 모습을 먼저 보여준다. AI⊃ML⊃DL은 기술의 포함 관계이고 **Computer Vision은 별도 시각 문제 분야**다. CNN은 DL 아키텍처의 한 사례일 뿐이다. P03에서 반복 검사 필요성 제시.
2. **P05~P08:** Grayscale `H×W` 2축 → P06 기존 RGB Pixel 클릭 상호작용의 `[R,G,B]` 3값 → P07 RGB 전체 `H×W×3` 3축 → P08 **같은 RGB 사과 이미지를 시간 순서대로 4장 대표 Frame으로 나열하는 그림을 먼저 보여주고 마지막에 `T×H×W×3` 4축** 정리. 실제 MP4 압축 파일 자체는 4D 배열 아님. `2차원/3차원/4차원`은 배열 축 수이지 공간 차원 아님.
3. **P15~P18:** 수동 덧셈 규칙, 조명에 따라 복잡해지는 사과 결함 규칙, 기존 모델 검증·필요시 추가 학습, 각 Task별 Label 형식을 설명한다. **P17에서 P02 포함관계 그림을 반복하지 않는다.**
4. **P19~P36:** 먼저 **왜 CNN의 작은 지역 필터가 필요한가**(P19), 그다음 교육용 **CNN 전체 Architecture**(P20), P21~P27 단일 뉴런·AND/XOR·ReLU, P28~P36 Kernel/Feature Map/Stride/Padding/Pooling/Head 확대. P20 Figure를 이후 장표에 **축소 미니맵**으로 재사용한다.
5. **P37~P55:** 데이터를 잘 나누고 Label/Loss/Gradient/Weight로 학습한 다음 독립 평가하고 처음 사과 결함 문제로 돌아온다.

**P20 교육용 가상 구조:** `RGB 사과 64×64×3 → Conv A(3×3 Kernel, 8 filters, stride1, padding1) → Feature Map 64×64×8 → ReLU → Max Pool(2×2,stride2) → 32×32×8 → Conv B(3×3,16 filters,stride1,padding1) → 32×32×16 → ReLU → Global Average Pool(16) → Dense Head(2) → 정상/불량 Score`. **학습 Weight=Conv/Head**, **고정 연산=ReLU/Max Pool**, **연산 속성=Stride/Padding**. 실제 훈련된 사과 결함 모델의 정확도·성능을 뜻하지 않으며 모든 CNN이 이 구조를 사용하지 않는다.

### A. Vision AI 개관·기술 관계·Pixel·영상·어려움 — 13장 / 26분

#### P01 · Vision AI란 무엇인가? · 사과 사진·영상에서 결함 찾기

- **ID / 원본 / 시간 / 변경:** `P01` · I01 / `data-concept="start"` · 1.5분 · 유지. 전역 계획 번호 1.
- **학습 목표와 핵심 메시지:** Vision AI는 이미지·동영상의 시각 정보를 AI로 분석하여 판단을 돕는 기술이며, 사과 표면의 작은 갈색 반점을 검사하는 것이 강의 전체의 중심 사례임을 설명한다.
- **교육 의도·교수 흐름:** 사과 원본 사진 제시→'어디가 문제일까요?' 질문→사진 또는 카메라 영상의 시각 입력→Vision AI 분석→결함 의심 여부·위치의 개념적 출력→AI·ML·DL/CV 관계, Pixel, CNN, 데이터 학습을 배워야 하는 이유를 예고. Task별 Output 정의나 CNN 구조는 다음 장들에서 다룬다.

#### P02 · AI·ML·DL과 Computer Vision의 관계

- **ID / 원본 / 시간 / 변경:** `P02` · 신규 승인 / `data-concept="ai-ml-dl-cv"` · 2분 · 신규 Intro. 전역 계획 번호 2.

- **Figure 명세(입력→처리→출력):** **왼쪽 53%** '해결하는 기술': AI 큰 박스 안 ML, 그 안 DL의 3중 Nested 상자, 각 상자 설명 한 줄, 가장 안쪽에 작은 'CNN(딥러닝 모델 구조의 한 예)' 태그. **오른쪽 47%** '해결할 시각 문제': 별도 Computer Vision 상자에 ① 전통적 이미지 처리(색상 임계값/윤곽 검출) ② AI 기반 이미지 분석(사과 결함 분류·위치 찾기)을 상하 두 줄로 배치. **AI 영역→CV의 AI 기반 카드**로 향하는 굵은 단일 화살표 위에 'Vision AI'. 하단 작은 사과 사진→결함 찾기 예. **CV를 DL 내부에 넣지 않으며 CNN이 유일한 Vision AI 구조처럼 표현하지 않는다.**

- **Reviewer 검수·완료 판정:** AI/ML/DL 포함관계, CV의 문제영역 성격, CNN은 DL의 한 예, 전통적 CV도 가능함을 수강생이 그림만 보고 설명한다. Vision AI를 20초 안에 한 문장으로 정의한다.

#### P05 · 흑백 사진은 H×W · 2차원 숫자 배열

#### P08 · 동영상은 시간순으로 이어진 RGB 이미지 여러 장

- **ID / 원본 / 시간 / 변경:** `P08` · 신규 승인 / `data-concept="video-frames"` · 2분 · 승인 Frame 중심 Figure 명세. 전역 계획 번호 8.
- **학습 목표와 핵심 메시지:** 동영상은 디코딩해 얻은 **RGB 프레임 여러 장이 시간 순서로 이어지는 것**으로 이해한다. 한 Frame은 `H×W×3`, Frame을 T장 쌓아 나타낸 교육용 숫자 배열은 `T×H×W×3`이며 4차원은 물리적 공간이 아닌 **배열 축의 개수**다.
- **교육 의도·교수 흐름:** P07 RGB 이미지 한 장을 그대로 회수→'이 사과가 조금 움직인 사진이 4장 연속 나타난다면?'→같은 사과 이미지의 미세한 위치 변화가 있는 대표 Frame 4개를 **시간 →** 순서로 봄→각 Frame은 같은 `H×W×3` 구조임을 확인→**맨 마지막에만** 동영상 `T×H×W×3`과 1초×30fps=30 Frame을 정리→P09 해상도 변화, P39 같은 영상 Group Split으로 연결.
- **앞뒤 연결:** 이전 P07 `RGB Image = H×W×3` 한 장을 **왼쪽 기준 그림으로 그대로 재사용** → 이번 P08에서 동일한 RGB 이미지가 시간축에 따라 반복된다는 사실만 추가 → 다음 P09 해상도에서는 각각의 Frame도 Pixel을 축소하면 작은 결함이 사라질 수 있음을 확인한다. 이후 P39 영상 그룹 분할에서 시간적으로 가까운 Frame의 높은 유사성을 회수한다.
- **Figure 명세(입력→처리→출력):** **가로 3구역 HTML/SVG 개념도**. **① 왼쪽 30%: 'RGB 이미지 한 장'** — 이전 P07의 공통 사과 사진(동일한 결함 ROI)을 크게 보여주고 `Image = H×W×3` 라벨, 선택 Pixel에 작은 `[R,G,B]` 말풍선 하나. **② 가운데 45%: '시간에 따른 RGB 프레임'** — 같은 사과의 모습을 조금씩 수평 이동시킨 작은 카드 **4장**을 왼쪽에서 오른쪽으로 배열하고 `Frame 1`, `Frame 2`, `Frame 3`, `… Frame 30` 라벨을 붙인다. 카드 상단 또는 하단에 **`시간(time) →`** 굵은 한 방향 화살표. 첫 카드 옆에만 `각 Frame = H×W×3` 표기, 나머지는 같은 구조라는 시각적 반복으로 전달. 실제로 30장이 모두 보이는 것이 아니라 **'1초 30fps 중 대표 4장만 표시'**를 명시한다. Frame 카드에서 사과는 같은 색·같은 결함 부위를 유지하고 **위치만 조금씩 다르게** 표현한다. 배경/사과를 완전히 다른 사진으로 바꾸지 않는다. **③ 오른쪽 25%: '동영상(프레임 묶음)'** — 가운데 카드 4장을 큰 묶음 중괄호 또는 스택 아이콘으로 받아 `Video` 와 `T×H×W×3`을 마지막에 표시, 바로 밑 `T = 시간순 프레임 수` 안내. **하단 한 줄 정리:** `RGB Image: H×W×3` → `RGB Frames × T` → `Video: T×H×W×3`. **우선순위: 사과 프레임 4장을 가장 눈에 띄게**; 배열 식은 중간 크기로, 코덱/Decoder는 본문 Figure에서 제외한다.
- **수식·수치·기존 자산/참고:** 대표 예시 `1초 × 30fps = 30 Frame`, `T=30`; 예시의 각 Frame `640×960×3`, 교육용 시퀀스 `30×640×960×3`. 전체는 `55,296,000`개의 **디코딩 후 비압축 채널 값**이며 비디오 파일의 바이트 크기나 AI 모델이 반드시 전부 받는다는 의미가 아니다. 메인 본문에서는 값의 총합 계산을 **작은 발표자 노트로 이동**해 2분 발표의 주제를 흐리지 않는다. 기존 사과 이미지 `docs/assets/vision_task_apple_reference.jpg` 재사용, 시간에 따른 이동은 실제 동영상 캡처가 아닌 **교육용 시뮬레이션**으로 표시.
- **Builder 구현 지시:** **우선순위가 가장 높은 Figure:** 좌 30% `RGB Image H×W×3` 공통 사과 1장→가운데 45% **같은 사과**의 RGB 대표 Frame 카드 네 장(1,2,3,…30), 위치만 조금씩 변형, 카드 위 **시간 화살표 →**→우 25% Frame 묶음 `Video = T×H×W×3`. 오른쪽 수식은 마지막에 읽히도록 배치. `1초 30fps / 대표 4장만 표시`, `이동은 교육용 시뮬레이션`, `압축 비디오 파일은 디코딩 후 Frame으로 다룸`을 작은 Caption으로. **MP4 Decoder 아이콘을 도식의 주인공으로 만들지 말 것.** 추가된 시간 축 T와 디코딩 Frame 개념 외 코덱·Tracking은 제외.
- **Reviewer 검수·완료 판정:** ① RGB 한 장→같은 사과 Frame 네 장→Video 묶음 순서가 한눈에 보인다 ② 모든 Frame은 `H×W×3`, `T=30`은 30fps의 1초 예시임을 안다 ③ 4장 대표 화면을 실제 4fps/총 4프레임으로 오해하지 않는다 ④ MP4가 원래 4D 배열이라고 주장하지 않는다 ⑤ 가상 움직임·사과 ROI·2분 설명이 정확하다.

- **ID / 원본 / 시간 / 변경:** `P26` · C12 / `data-concept="relu"` · 2분 · 이동·C13 이후. 전역 계획 번호 26.
- **학습 목표와 핵심 메시지:** Architecture의 ReLU는 가중합을 꺾는 비선형 연산 `max(0,z)`이며 여러 층을 결합할 때 복잡한 패턴을 표현하도록 돕는다.
- **교육 의도·교수 흐름:** 평범한 직선 y=z와 ReLU를 같은 눈금에 비교→-2,2의 출력을 직접 읽기→다음 XOR 실습으로
- **앞뒤 연결:** 이전 P25 비선형성 · 깊어져도 직선이면? → CNN Architecture에서 ReLU(비선형성)가 필요한 이유 → 다음 P27 XOR · 선형층을 쌓아도 직선 하나.
- **Figure 명세(입력→처리→출력):** 왼쪽 y=z, 오른쪽 y=max(0,z) 2개 좌표 그래프 동일 축·원점·-2/2 화살표; 꺾이는 원점 강조
- **수식·수치·기존 자산/참고:** ReLU(-2)=0,ReLU(2)=2; 단일 ReLU 하나로 XOR 해결한다고 말하지 않음
- **Builder 구현 지시:** P20 공통 Architecture 미니맵에서 **ReLU** 영역을 강조한다. 그래프 축 동일 범위, 0 미만과 이상 색상 구분. 디자인은 기존 레이아웃의 figure 형식과 간격을 유지; 핵심 비교나 대응 관계는 실제 화살표·동일 색상의 좌표/ROI 강조로 표시한다.
- **Reviewer 검수·완료 판정:** ReLU가 비선형이라는 사실과 XOR 해결에 여러 조합 필요함을 구분. 별도로 사실성/증거 수준 Caption과 다음 장 선행지식이 맞는지 확인한다.

#### P27 · XOR · 선형층을 쌓아도 직선 하나

- **ID / 원본 / 시간 / 변경:** `P27` · C11 / `data-concept="xor-gate"` · 5분 · 이동·ReLU 이후·실습. 전역 계획 번호 27.
- **학습 목표와 핵심 메시지:** 선형2층의 단일 직선 한계와 비선형 조합의 XOR 분리 효과를 비교한다
- **교육 의도·교수 흐름:** 정답 고정→비선형 없음 모드 W1,b1,W2,b2 조절·최대3/4→비선형 모드 전환·4/4→복잡한 경계
- **앞뒤 연결:** 이전 P26 ReLU · 비선형성의 시작 → CNN Architecture에서 ReLU(비선형성)가 필요한 이유 → 다음 P28 Kernel · 작은 영역의 가중합.
- **Figure 명세(입력→처리→출력):** 좌 4슬라이더(각 층 W,b), 중간 레이어 두 단 1과 2, 우측 좌표평면; 모드 토글 '선형/|t|'; 경계 갱신과 4개 점 정확도 동기화
- **수식·수치·기존 자산/참고:** t=W1*x1+x2+b1,z=W2*g(t)+x1+b2; 비선형 g(t)=|t|=ReLU(t)+ReLU(-t); x1,x2 고정 계수1 구분
- **Builder 구현 지시:** P20 공통 Architecture 미니맵에서 **ReLU 효과** 영역을 강조한다. 비선형 없는 상태에서 조합이 하나의 Affine인 점, |t|는 ReLU 두 반응 합이라는 사실 명시. 디자인은 기존 레이아웃의 figure 형식과 간격을 유지; 핵심 비교나 대응 관계는 실제 화살표·동일 색상의 좌표/ROI 강조로 표시한다.
- **Reviewer 검수·완료 판정:** 실시간 조작으로 선형3/4, 비선형4/4를 재현하고 임의 상태 리셋 가능. 별도로 사실성/증거 수준 Caption과 다음 장 선행지식이 맞는지 확인한다.

- **Reviewer 보강 (AUD-02·AUD-06):** 비선형 없음 모드에서 `g(t)=t`, `t=W1·x1+x2+b1`, `z=W2·t+x1+b2`이므로 `z=(W2·W1+1)x1 + W2x2 + (W2b1+b2)`. 이 경계는 **기울기도 절편(위치)도 달라질 수 있지만 언제나 하나의 선형 결정 경계**라는 점을 슬라이더 옆에 한 줄로 고정한다. W1·W2·b1·b2의 네 슬라이더, x1→두 번째 층 고정 연결 `+x1`, t 안 x2 계수1을 화살표에 표시한다. `선형 3/4` 및 `비선형 4/4`는 제공하는 **재현 가능한 프리셋의 결과**로 표시하고 모든 임의 설정에서 항상 달성한다고 단정하지 않는다.

- **비선형 버튼 및 Figure 동기화:** P25에서 Affine 합성 한계, P26에서 `ReLU(t)=max(0,t)`를 먼저 설명한 뒤 P27에서 `g(t)=|t|=ReLU(t)+ReLU(-t)`로 전환한다. **단일 ReLU가 XOR을 곧바로 해결한다는 그림 금지**. 그래프의 점 4개 정답, 프리셋 예측, 경계 모양, 점수 3/4→4/4, 식, 토글 상태를 한 상태로 연결하고 `Reset→linear preset→nonlinear preset→Reset` 순으로 두 viewport에서 실행 검수한다. 1366×768에서 프리셋 상태가 보이는지, 수식/결정경계와 UI 값이 일치하는지 확인한다.

- **Reviewer 검수·완료 판정:** 지도/비지도 구분은 Label 유무/목표, 비지도 그룹 해석 미확정. 별도로 사실성/증거 수준 Caption과 다음 장 선행지식이 맞는지 확인한다.

- **Reviewer 보강 (AUD-09) / 중앙 공통 Backbone 우선:** 슬라이드 중앙 넓은 영역에 `입력 사과 여러 장 → 동일한 사전학습 CNN Extractor [FROZEN, 학습하지 않음] → 같은 Feature Vector`를 **한 번만** 크게 배치한 후 좌/우 두 분기. **좌(지도 활용)** = 정상/불량 **Label 있음** → Classifier Head Weight 학습 + Label 기반 Loss → 정상/불량 Prediction. **우(비지도 후단 활용)** = **Label 사용 안 함** → 고정 Feature를 K-means 군집화(군집 중심 등 후단 파라미터 계산) → Group A/B. Group A/B에 `정상`/`불량` 이름, 색상 또는 정확도를 대응시키지 않는다.

- **P46 학습 범위와 검수:** 이 그림은 **동일한 고정 pretrained Backbone 위의 서로 다른 후단 활용 방법**이지 CNN 전체를 지도학습/비지도학습하는 두 방법의 비교가 아니다. Backbone은 두 경로 모두 Freeze이고 지도 Head만 Gradient로 갱신한다. 비지도 군집은 Label 없는 특징 집합에서 중심을 추정하며 동일한 Classifier Loss나 정답 예측이라고 표현하지 않는다. 라벨 사용 유무와 후단 목표가 Backbone/head 형태보다 먼저 읽히도록 2열 보조 설명을 최소화. 두 해상도에서 중앙 공통 입력/분기선, Freeze 표시, 좌/우 Label/No Label, 군집 결과 색상 범례를 검수한다.

## 4. 첫 번째 Builder 제작 단원 — Rule-based vs 데이터 학습 2장 (우선순위 P0)

**Builder 첫 구현 단원:** 현행 `C02 rules` → `C03 rules-image`의 Figure·부제·Takeaway만 우선 보완. P14(C01)의 Task 정의 및 P17(C05)의 모델 선택은 연결 문구만 검사하고, 다른 강의 HTML 구조·CSS 전역 변경은 범위 밖이다. C02는 명확히 정의한 더하기 규칙, C03은 예외가 많은 이미지 결함 판정과 라벨 기반 지도학습을 대비한다.

### Builder 작업 스펙

**1장(C02/P15, 2분) — '규칙이 명료할 때는 사람이 알고리즘을 쓸 수 있다'.**
- 중앙 Figure를 **동일 규칙의 재사용**에 집중: 왼쪽 `1+1`, `2+1` 입력 카드→가운데 단 하나의 규칙 블록 `f(a,b)=a+b`→오른쪽 각각 `2`, `3`. 두 입력이 다른데 규칙 블록은 동일하고, 화살표 2쌍을 빠짐없이 연결한다.
- 덧셈 공식은 인간이 직접 정한 처리 규칙. '예시를 보여주고 덧셈 학습'처럼 그리지 않음. 상단 질문 "어떤 문제는 왜 ML이 필요 없을까?" 하단 "판단 규칙이 명확하면 학습 없이도 된다".
- 다음 장 연결: "그런데 사과 반점의 모든 색·크기·조명 조건을 하나의 문장으로 표현할 수 있을까?"

**2장(C03/P16, 2.5분) — '이미지에서는 예외를 일일이 쓰기보다 정답 사진으로 학습할 수 있다'.**
- **동일 입력 비교**를 명시: 밝은 불량 사과, 어두운 불량 사과, 어두운 정상 사과를 좌/우 경로 모두에서 같은 썸네일/라벨로 제시. 기존 생성 사진과 CSS 밝기 변환 재사용. 실제 서로 다른 원본 사진과 단일 사진 밝기 시뮬레이션을 구분.
- **좌측 Rule-based:** "갈색 Pixel 수가 k 이상이면 불량" 조건 블록→'그림자/어두운 조명도 조건에 걸림?' 의문 기호→조건 추가 필요. 조건 자체가 나쁜 것이 아니라 현장 변화가 늘 때 **수동 설계·유지보수 비용**이 커지는 사례.
- **우측 지도학습:** 같은 썸네일+정상/불량 Label→Training→'학습된 판단 기준' Model 블록→새 사진에서 Prediction→Validation/Test로 일반화 확인. 학습된 가중치·정확도·모델 예측 결과는 실제 측정으로 만들거나 주장하지 않음.
- 결론은 이분법 금지: Rule-based도 유효하고, ML도 틀릴 수 있음. 촬영 조건과 과제 요구에 따라 선택한다. 다음 P17(C05)의 '기존 모델부터 시험'으로 연결.
