## 1. 설계 목표와 냉정한 진단

**한 문장 중심 질문:** "카메라의 사과 사진·연속 촬영 동영상은 컴퓨터에서 어떻게 숫자가 되고, 그 숫자에서 결함을 찾는 모델은 어떻게 학습할까?"

### 최우선 학습 목표 (2026-10-19 Draft 보완)

**G1. 이미지와 동영상을 컴퓨터가 어떻게 수치 데이터로 받아들이며, 그 때문에 Vision AI가 왜 어려운지를 이해한다.**
- 정지 이미지: Pixel·RGB의 의미, `H×W×3` 배열과 해상도가 보존하거나 잃는 정보를 설명한다.
- 동영상: 압축 영상 파일을 디코딩하면 시간 순서가 있는 여러 Frame을 얻고, 각 Frame은 하나의 이미지 배열임을 이해한다. 교육용 영상 클립의 표현은 `T×H×W×3`이고 `T`는 Frame 수이다. 이는 압축 파일 자체의 데이터 구조나 모든 실제 동영상 모델의 입력 형식과 같다는 뜻이 아니다.
- Vision AI의 난점: 같은 대상도 조명·회전·원근·가림·흐림·움직임에 따라 Pixel 값과 Frame 배치가 달라진다. 큰 변화는 무시하고 작은 지정 결함은 감지해야 하며, 동영상에서는 시간적 순서와 인접 프레임의 높은 유사성도 고려해야 한다.

**G2. 컴퓨터의 머신러닝 모델이 데이터로부터 어떻게 판단 규칙을 학습하는지 이해한다.**
- 사람이 판단 규칙을 직접 지정하는 Rule-based와, 이미지·프레임 및 정답 Label로 Weight를 조정하는 Machine Learning의 차이를 설명한다. **'알아서 학습'은 사람이 목표·Label·Loss·Architecture를 지정한 다음, 데이터로 모델 Weight를 최적화한다는 뜻**이다.
- CNN이 머신러닝(ML) 안의 딥러닝(DL)에 속하는 **이미지 처리에 적합한 신경망 아키텍처 한 종류**임을 설명한다.
- CNN Architecture의 전체 그림을 먼저 본 다음 그림 속 Kernel·Feature Map·ReLU(비선형성)·Stride·Padding·Max Pooling·Channel·Head를 쉬운 숫자 예시로 설명한다.
- `입력 데이터→CNN 특징 계산→예측→Label과 비교→Loss→Gradient/Optimizer→Weight 갱신→반복`의 학습 순환을 직관적으로 설명한다.
- Training과 Inference의 차이를 구분하고, 새로운 촬영 조건에 일반화하는지는 독립 Validation/Test로 확인해야 함을 이해한다.

**세부 학습 성과:** G1·G2를 위한 Task별 Classification/Detection/Segmentation 출력·Label 선택, Perceptron·AND/XOR·ReLU·CNN Kernel/Feature Map의 역할, Train/Validation/Test·FN/FP·Precision/Recall의 의미를 연결한다. 코딩, 수학적 증명, 동영상 Tracking 알고리즘은 범위에서 제외한다.

**강의 인과관계:** 이미지/영상 수치 입력(G1) → Rule-based vs ML → **ML 안의 DL, 그 안의 CNN 아키텍처** → **CNN의 전체 구조를 먼저 제시** → 각 Layer/설정(ReLU·Conv·Kernel·Stride·Padding·Max Pool·Head)을 하나씩 확대 → 데이터·Label로 가중치 학습 → 평가(G2).

**장점:** 같은 사과 검사 사례, 실제 클릭 Pixel/RGB, 명확한 덧셈 규칙 2예제, AND/XOR 슬라이더, 동일 5×5/3×3 Kernel→Feature Map 연속 수치, SqueezeNet 실제 일부 특징 출력, 동일 교육용 평가 100건의 내부 일관성.
**P0:** I13은 I09~12의 원인/사례를 반복한다; C11은 ReLU를 소개하기 전에 `|t|` 비선형 효과를 조작해 선행지식이 뒤바뀐다; C42~44는 워크플로·과제정의·Threshold 실습을 중복한다.
**P1:** 현행 Intro의 정지 이미지 Pixel 설명은 풍부하지만 동영상의 Decoder→Frame→시간축은 독립적으로 설명되지 않아 Video Group Split의 선행지식이 부족하다. C04/C05/C06에는 기존 모델과 방법 선택의 반복이 있다; C14가 CNN 전체 Architecture부터 먼저 시작해 "왜 지역·공유 구조인가?"라는 요구가 C15에 늦게 나온다; C27의 비디오 그룹 예시는 사과 연사/같은 제품 그룹과 추가 연결이 필요하다; CNN의 30분 11장은 압축하지 말고 계산 중심 우선순위를 구분해야 한다.
**기술적 주의:** 단일 뉴런의 가중치 개수 ≠ 뉴런 수. 공유 W의 `z=W(x1+x2)+b`는 특별 예시. AND 실습은 `z=Wx1+x2+b`이며 같은 W 가정과 다르다. Affine 합성은 Affine. XOR 비선형 예시의 `|t|`는 ReLU 두 개의 합. C34 고정 Backbone의 후단 지도/비지도 활용 ≠ 전체 CNN 학습 방법의 구분. 고정 Score는 calibrated probability가 아니다.

### 핵심 교수 전략 · CNN Architecture를 먼저 보여준 후 Zoom-in

1. **Rule-based vs ML:** 사람이 조건을 직접 작성하는 방식과, 사람의 정답 Label을 바탕으로 모델 Weight를 조정하는 방식을 사과 사례로 비교한다. ML⊃DL⊃CNN의 포함 관계를 보여준다. CNN은 유일한 Vision AI 모델이 아니라 DL 모델 **아키텍처의 한 사례**이다.
2. **CNN 전체 구조 공개 (P21):** 화면 가로 한 줄에 `사과 RGB 64×64×3 → Conv A (3×3, 8 filters, stride 1, padding 1) → Feature Map 64×64×8 → ReLU → Max Pool (2×2, stride 2) → 32×32×8 → Conv B (3×3, 16 filters, stride 1, padding 1) → 32×32×16 → ReLU → Global Average Pool(16) → Dense Classification Head(2) → 정상/불량 Score`를 연결한다. **이 모델은 교육용 가상 구조**이며 실제 결함 검사에 충분한 해상도/정확도를 의미하지 않는다.
3. **전체 구조의 한 부분씩 확대:** P22–P19은 아키텍처에 등장한 ReLU가 필요한 이유(퍼셉트론→AND/XOR→Affine 한계→ReLU), P27–P32는 Conv 안에서 Kernel·Feature Map·Weight Sharing·Channel·Stride·Padding, P33은 Max Pool, P34–P35는 Feature Map·Head를 설명한다.
4. **재사용 가능한 Figure:** P21 전체 구조는 HTML/SVG로 자체 제작. 입력→Conv/Map→ReLU→Pool→Conv→Head→Output 화살표와 Shape가 대응한다. 파란 Extractor/초록 Head로 역할을 구분한다. **학습할 Weight는 Conv 및 Dense Head**에 있고 ReLU와 일반 Max Pool은 고정 연산이다. Stride와 Padding은 레이어가 아닌 연산 설정이다. P22–P35의 우상단에 동일 Architecture 미니맵을 넣고 현재 설명 블록만 강조한다.
5. **개념별 질문:** Kernel '왜 작은 영역만 볼까?' → Feature Map '같은 Kernel을 이동하면?' → ReLU '직선만 겹치면 복잡한 기준을 배울 수 있을까?' → Stride '한 칸/두 칸 움직이면?' → Padding '가장자리는?' → Max Pool '가장 큰 특징만 남기면?' → Head '특징을 어떻게 정상/불량 결과로 바꿀까?'. 각 개념은 Architecture 속 위치→필요 이유→작은 숫자 예시→출력의 순서로 설명한다.

**검수 기준:** 출력 Shape `64×64×3→64×64×8→32×32×8→32×32×16→16→2`; CNN 패턴은 하나의 예시이며 모든 CNN에 Pool·GAP가 필수는 아님. 레퍼런스: Stanford CS231n https://cs231n.github.io/convolutional-networks/ .

#### P07 · 동영상은 프레임의 연속 · 시간축 추가

- **ID / 원본 / 시간 / 변경:** `P07` · 신규 Draft / `data-concept="video-frames"` · 2분 · 신규. 전역 계획 번호 7.
- **학습 목표와 핵심 메시지:** 컴퓨터는 동영상을 디코딩해 얻은 시간 순서의 이미지 Frame들로 다룰 수 있다. 각 Frame은 Pixel을 가진 정지 이미지이고, 연속 Frame에는 시간축이 더해진다. (G1)
- **교육 의도·교수 흐름:** P06에서 한 사진의 RGB 배열 확인 → 압축 영상 파일 → Decoder → 시간 순서에 따른 Frame → 각 Frame의 RGB 숫자 → 인접 Frame이 닮았어도 움직임·빛 변화로 같은 사과의 값과 위치가 달라짐 → 다음 해상도와 촬영 조건 변화의 어려움으로 연결.
- **앞뒤 연결:** 이전 P06 `H×W×3` 정지 이미지 한 장을 하나의 Frame으로 회수 → 다음 P08 해상도에서는 영상의 각 Frame도 작은 결함이 축소로 사라질 수 있음을 살펴본다. 이후 P38 그룹 분할에서 같은 영상의 인접 Frame들이 유사한 이유를 회수한다.
- **Figure 명세(입력→처리→출력):** 가로 화면 좌측 `camera_clip.mp4` 파일 아이콘 → 가운데 `Decode` 블록 → 오른쪽 시간축 `t=0, 1/30, 2/30, …, 29/30초` 위에 30개 Frame 눈금과 대표 Frame 4개를 큰 썸네일로 배치. 동일한 결함 사과를 각 Frame에서 조금씩 옮기되 움직임은 교육용 시뮬레이션임을 명시. 첫 Frame의 동일 결함 ROI 한 곳을 아래로 확대해 `640×960×3` RGB 채널 격자/숫자에 연결. 하단 `정지 이미지 = H×W×3`, `연속 Frame = T×H×W×3` 비교와 시간 방향 화살표. 실제 코덱 바이트를 프레임 배열처럼 그리지 않음.
- **수식·수치·기존 자산/참고:** 예시 `30 fps × 1초 = 30 Frame`. Frame당 `640×960×3 = 1,843,200` 숫자 값; 전체 `30×640×960×3 = 55,296,000` **비압축 채널 값**(비디오 파일 크기 아님). `docs/assets/vision_task_apple_reference.jpg` 재사용. 실제 촬영 영상/모델 결과가 아닌 생성 시나리오를 정확히 표시.
- **Builder 구현 지시:** 한 장에서 'Frame은 이미지이고 동영상은 시간 순서가 있는 Frame들의 모음'만 설명한다. CSS/SVG Filmstrip/Decoder/시간축/숫자 격자를 설계하고, 표시는 사과 원본의 교육용 변화로 한정한다. 실제 모델은 Frame 일부를 추출할 수 있고 코덱·영상 Tracking은 이 강의의 범위를 벗어난다는 각주. 기존 HTML은 Draft 승인 전에 수정하지 않는다.
- **Reviewer 검수·완료 판정:** Decoder 이전 압축 파일과 디코딩된 영상 Frame을 구분한다. `T×H×W×3`이 **교육용 Frame 배열**임을 표시하고, 30 fps/1초/30 Frame과 55,296,000개 **수치 값**을 재계산한다. 시간 순서·위치 변화·인접 Frame 유사성이 후속 Vision의 어려움 및 그룹 분할과 연결되는지 검수한다.

## 4. 첫 번째 Builder 제작 단원 — Rule-based vs 데이터 학습 2장 (우선순위 P0)

**승인 후 첫 작업:** 현행 `C02 rules` → `C03 rules-image`의 Figure·부제·Takeaway만 우선 보완. C01의 Task 정의 및 C05의 모델 선택은 연결 문구만 검사하고, 다른 강의 HTML 구조·CSS 전역 변경은 범위 밖이다. C02는 명확히 정의한 더하기 규칙, C03은 예외가 많은 이미지 결함 판정과 라벨 기반 지도학습을 대비한다.

### Builder 작업 스펙

**1장(C02/P14, 2분) — '규칙이 명료할 때는 사람이 알고리즘을 쓸 수 있다'.**
- 중앙 Figure를 **동일 규칙의 재사용**에 집중: 왼쪽 `1+1`, `2+1` 입력 카드→가운데 단 하나의 규칙 블록 `f(a,b)=a+b`→오른쪽 각각 `2`, `3`. 두 입력이 다른데 규칙 블록은 동일하고, 화살표 2쌍을 빠짐없이 연결한다.
- 덧셈 공식은 인간이 직접 정한 처리 규칙. '예시를 보여주고 덧셈 학습'처럼 그리지 않음. 상단 질문 "어떤 문제는 왜 ML이 필요 없을까?" 하단 "판단 규칙이 명확하면 학습 없이도 된다".
- 다음 장 연결: "그런데 사과 반점의 모든 색·크기·조명 조건을 하나의 문장으로 표현할 수 있을까?"

**2장(C03/P15, 2.5분) — '이미지에서는 예외를 일일이 쓰기보다 정답 사진으로 학습할 수 있다'.**
- **동일 입력 비교**를 명시: 밝은 불량 사과, 어두운 불량 사과, 어두운 정상 사과를 좌/우 경로 모두에서 같은 썸네일/라벨로 제시. 기존 생성 사진과 CSS 밝기 변환 재사용. 실제 서로 다른 원본 사진과 단일 사진 밝기 시뮬레이션을 구분.
- **좌측 Rule-based:** "갈색 Pixel 수가 k 이상이면 불량" 조건 블록→'그림자/어두운 조명도 조건에 걸림?' 의문 기호→조건 추가 필요. 조건 자체가 나쁜 것이 아니라 현장 변화가 늘 때 **수동 설계·유지보수 비용**이 커지는 사례.
- **우측 지도학습:** 같은 썸네일+정상/불량 Label→Training→'학습된 판단 기준' Model 블록→새 사진에서 Prediction→Validation/Test로 일반화 확인. 학습된 가중치·정확도·모델 예측 결과는 실제 측정으로 만들거나 주장하지 않음.
- 결론은 이분법 금지: Rule-based도 유효하고, ML도 틀릴 수 있음. 촬영 조건과 과제 요구에 따라 선택한다. 다음 C05의 '기존 모델부터 시험'으로 연결.

### Builder 파일 변경 경계

대상 후보: `docs/vision_ai_course.html`의 `[data-concept="rules"]`·`[data-concept="rules-image"]`, `docs/rules_vs_learning.css` 스코프만. 기존 사진 `docs/assets/vision_task_apple_reference.jpg`, `docs/assets/generated/apple_studio_preview.png` 재사용. 새로운 글로벌 CSS, 라이브 모델 호출, 외부 이미지 hotlink, Preprocessing 별도 장표는 추가하지 않는다. 두 장의 `data-concept` 및 C01/C05 네비게이션 유지. 이후 신규 54장 재편은 별도 승인·별도 Builder 단계로 취급.

### 1차 작업 완료 기준

1. C02에서 서로 다른 숫자 입력 2개가 같은 규칙을 통해 정확히 2와 3을 만들며, 새 학습이 등장하지 않는다.
